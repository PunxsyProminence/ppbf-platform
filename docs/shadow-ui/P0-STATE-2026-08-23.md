## P0.1 — NOT DONE. The only item with a live art-policy violation.

`apps/web/components/SignInPanel.tsx:375-386` renders the `?error=`
query-param refusal as a hand-built red panel:

```jsx
className="… border-2 border-[color:var(--locked)] bg-[rgba(168,30,34,0.06)] …"
  <span className="badge badge--locked"><i>✕</i>Sign-in refused</span>
```

`--locked` and `badge--locked` are the safety red. `RefusalStamp.tsx:10-14`
states the rule: *"MEDICALLY_NOT_ALLOWED is the only kind that may use the red /
--locked treatment"* — every other kind, including TRAINING_HOLD, renders
brass/bone, *"even though Law 2 would technically allow --locked more broadly for
a refusal."* A sign-in refusal is not medical.

Two things make this precise rather than a matter of taste:

- **The same file already states the rule and already obeys it twice.** Line 89
  records that a 429 is a WAIT and not a refusal *"because the owner's locked
  art policy reserves red/--locked for medical/safety only"*. The PIN path
  (line ~453) and the magic-link path (line ~561) both render `RefusalStamp`.
  Only the `?error=` panel is left.
- **The comment above the panel argues the red is acceptable** because a glyph
  and a label accompany it. That is Law 3 reasoning and it is sound as far as
  Law 3 goes. The art policy is *narrower* than Law 3, and the narrower rule
  governs.

Six `?error=` values reach `authErrorMessage` (`SignInPanel.tsx:~102`):
`not-invited`, `auth-state-expired`, `auth-forbidden`,
`privileged_auth_required`, `unsupported_role`, and a default. Each maps to a
`RefusalStampKind`; none maps to `medically_not_allowed`.
