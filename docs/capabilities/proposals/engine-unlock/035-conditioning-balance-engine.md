# Engine Unlock Proposal — Module 035 Conditioning Balance Engine

## Status

PROPOSAL — awaiting owner approval. No code.

The current module stub (`docs/capabilities/modules/035-conditioning-balance-engine.md`) is an empty scaffold: Status DRAFT, Active false, and every section (Intent, Boundaries beyond the three standard lines, Dependencies, Acceptance criteria) unfilled since the 2026-08-03 scaffold commit.

## (a) What the engine computes and shows

**What "balance" cannot honestly mean here.** A balance implies a target ratio — "60% skill work, 40% conditioning" or similar — and no such ratio is recorded, validated, or derivable from this platform's data. Per the honesty doctrine, this engine must never import one from strength-and-conditioning literature or invent one from a training-theory prior. Absent an owner-authored target (open question 1), this engine can only be a **descriptive composition report**: what mix of already-recorded, already-categorized training content an athlete (or org) actually got, expressed as counts and shares of recorded events — never scored, never graded against an ideal.

**Boundary against module 015 (Energy System Development Engine).** Module 015 already has its own detailed, unbuilt engine-unlock proposal (`docs/capabilities/proposals/engine-unlock/015-energy-system-development-engine.md`) that claims the *within-category* signals: a trend of conditioning-metric attempts over time (`pilot.training_attempts` where `metric_kind in ('time_seconds','hold_seconds','rounds')`), a conditioning-tagged load history (`pilot.session_load.rpe_physical`), a conditioned-sparring exposure trend (`pilot.sparring_exposure` where `sparring_type='conditioned'`), and scripted conditioning-block delivery (`pilot.session_script_blocks` where `block_kind='conditioning'`). Those are legitimate, single-bucket-over-time questions: "is conditioning happening, and how is it trending." **035 does not re-ask that question.** 035 asks a *cross-category* question instead: "of everything recorded, what share was conditioning-flavored versus everything else" — a composition/mix at one point in time or over a window, not a trend within one bucket. Concretely:
- 015 owns: conditioned-sparring segments *over time* (a trend line).
- 035 owns: conditioned segments *as a share of all recorded sparring segments this window* (hard/play/technical/game/conditioned side by side).
- 015 owns: conditioning attempt trend on one `metric_kind`.
- 035 does **not** duplicate that metric-kind trend at all — training_attempts has no category/type column that separates "conditioning work" from any other timed/counted attempt, so 035 has no honest composition signal to build there (see "What it does NOT compute" below).

Both modules read the same raw tables. Per the playbook's "prefer existing primitives over parallel sources of truth" rule and AGENT_KERNEL invariant 2 ("search before creating"), whichever of 015/035 ships first should own the per-category derivation query, and the second module should consume the first's computed per-category rows rather than re-deriving identical counts from the same raw tables a second time (open question 2). This proposal is written to stand alone if 035 ships first.

**What 035 CAN honestly compute and show**, all athlete-scoped and read-only against existing tables, each axis independently thresholded and never merged into one number:

1. **Sparring-type composition (strongest signal — DB-enforced closed vocabulary).** `pilot.sparring_exposure.sparring_type` is a real, `CHECK`-constrained vocabulary: `hard | play | technical | game | conditioned` (`pilot_sparring_exposure_type_check`). Grouping an athlete's `time_under_impact_sec` by `sparring_type` over a window and showing each type's share of total recorded time is a straightforward, honest description of the recorded mix — describing it, not judging it. "38% of your logged sparring time this window was type `conditioned`" is honest; "you should be closer to 25%" is a target and is owner doctrine, not something this engine may assert.
2. **Physical-vs-cognitive load composition.** `pilot.session_load.rpe_physical` and `rpe_cognitive` are already split by design (the migration's own comment: "a hard conditioning round and a hard sparring round can return the same number with entirely different recovery demands. Splitting them is what makes live work distinguishable from conditioning in the data"). Showing an athlete's average `rpe_physical` and average `rpe_cognitive` side by side over a window, each labeled with `rated_by` (`athlete` or `coach_proxy`), is a real two-fact composition. Per that table's own rule, the two are never combined into one number and no derived sRPE×duration figure is stored or computed here.
3. **Categorized-drill composition (weakest signal — free text, not DB-enforced).** `pilot.drills.category` is a real, populated field (seeded values include `conditioning`, `technical`, `footwork`, `tactical`, `strength`, `defense`, `sparring`, and others) but it carries **no** `CHECK` constraint — it is organization-editable free text, unlike `sparring_type`. Joining verified completions (`pilot.assignment_completions` where `verification_status='verified'`) through `pilot.drill_assignments.drill_id` (non-null only — legacy assignments carry `drill_id is null` and only free-text `drill_name`/`drill_description`, which cannot be categorized and must show as an explicit UNKNOWN, never assumed to be zero) to `pilot.drills.category` gives a real per-athlete count of verified, categorized completions by category, with `conditioning` broken out from every other category. This axis is explicitly labeled less authoritative than (1) and (2) because the vocabulary is not database-enforced (open question 4).
4. **Org-level template-library content mix (org only — no athlete equivalent exists).** `pilot.workout_template_items.contact_level` is itself a `CHECK`-constrained vocabulary that includes `conditioned` alongside `none | light_technical | controlled_sparring | open_sparring` (`pilot_wti_contact_level_check`), and `pilot.session_script_blocks.block_kind` is a `CHECK`-constrained vocabulary that includes `conditioning` alongside nine other kinds (`arrival, instruction, demonstration, drill_round, reset_minute, teaching_minute, transition, reflection, close`). Both tables carry **no athlete identifier and no completion state** — `pilot.workout_templates`' own migration comment says so explicitly ("A template is gym-wide coaching content... no completion state, no effectiveness score"), and `pilot.session_script_runs` records only `blocks_completed` (a count) and `athletes_present` (a count) per class run, never which specific athlete received which specific block. So this axis can only ever describe **what the gym's template library and scripts contain** — never what any specific athlete actually received. It is shown only at org level, explicitly labeled "library content, not delivered exposure."

**What it does NOT compute, at any data volume:**
- No target/ideal mix ratio, percentage-of-time-that-should-be-conditioning, or "balanced/unbalanced" verdict, ever, unless and until the owner authors one (open question 1) — and even then the target is owner doctrine data this engine displays, not something it derives.
- No energy-system or aerobic/anaerobic classification of any category (that is 015's territory, and 015's own proposal already refuses it at any data volume — no HR/VO2/lactate table exists anywhere in this schema).
- No composite "conditioning score," no dose scalar, no derived sRPE×duration figure as a stored or computed value.
- No trend-over-time within the `training_attempts` table by conditioning-vs-not, because that table's `metric_kind` (`reps, time_seconds, distance_m, load_kg, rounds, hold_seconds`) is a measurement-unit vocabulary, not a training-content-category vocabulary — there is no column on `pilot.training_attempts` that says whether a given attempt was conditioning work, skill work, or anything else. Inventing one here (e.g., inferring category from `context_type` or `note` free text) would be exactly the invented metric the honesty doctrine forbids.
- No per-athlete reading of `workout_template_items`/`session_script_blocks` as "what this athlete did" — those tables cannot support that claim (see axis 4 above).
- No cross-athlete comparison, ranking, or leaderboard of any mix, at any level.
- No AI-generated interpretation of a mix ("your balance looks off," "you need more conditioning") — only the recorded shares themselves, restated.

**Safety gating that must apply before any surface renders.** `pilot.training_holds.scope` includes `'conditioning_only'` and `'all_training'` (`pilot_slice_postgres_training_holds_migration.sql`). Exactly as 015's proposal requires, this engine must check `pilot.training_holds` (status = active, scope in `('conditioning_only','all_training')`) before rendering any conditioning-composition view for an athlete, and must never render progress-framed or encouragement language while such a hold is active — the historical record still shows, plainly, with a hold notice (see open question 1 in 015's proposal for the reasoning this engine inherits).

## (b) Data prerequisites

|---|---|---|---|---|
| Sparring-type composition | `pilot.sparring_exposure` (`sparring_type`, `time_under_impact_sec`, `athlete_id`) | ≥ 8 logged segments, spanning ≥ 2 distinct `sparring_type` values | trailing 60 days | A single segment or a single sparring_type ever logged cannot be shown as a "mix" — it is one data point dressed as a distribution. The 60-day window matches sparring's own low-frequency cadence (segments accrue per live session, not per attempt). **The specific counts (8 segments / 2 types / 60 days) are a judgment call — OWNER_DECISION** (open question 3 covers the analogous org-level number; this is the athlete-level twin). |
| Physical-vs-cognitive load composition | `pilot.session_load` (`rpe_physical`, `rpe_cognitive`, `rated_by`, `rated_at`) | ≥ 6 rated sessions with **both** `rpe_physical` and `rpe_cognitive` non-null | trailing 30 days | A row with only one of the two fields populated cannot show a "split" — both facts must exist for the same session. Six is lower than 015's 8-rating/4-week threshold for a conditioning-only trend because this is two parallel facts shown side by side, not a trend line requiring noise-resistance. **OWNER_DECISION** on the exact count. |
| Categorized-drill composition | `pilot.assignment_completions` (`verification_status='verified'`) joined `pilot.drill_assignments.drill_id` (non-null) joined `pilot.drills.category` | ≥ 6 verified, categorized completions, spanning ≥ 2 distinct `category` values | trailing 90 days | Longest window of the three because this signal requires the newer `drill_id`-linked assignment path *and* coach/verifier follow-through on `verification_status`, both of which are sparser than raw logging. Below 2 distinct categories, there is no mix to show — only a single category's count. **OWNER_DECISION.** An athlete with plenty of `drill_assignments` but none carrying `drill_id` sees an explicit "your assigned drills aren't in the catalog yet" state, distinct from "not enough data yet" (see (c)). |

## (c) LOCKED state

Athlete/parent view, before per-athlete prerequisites are met, shows real counts against real thresholds only — never a percentage bar, XP, points, or levels, and never a partial mix presented as if it were complete:

> **Conditioning mix: not enough logged yet to show your own recorded balance.**
> - Sparring-type mix: **5 of 8** segments logged, covering **1 of 2** needed distinct types, in the current 60-day window. *Next: log sparring segments with type recorded as they happen — the mix fills in as more types get logged.*
> - Physical/cognitive load split: **3 of 6** sessions rated with both physical and cognitive effort, across the last 30 days. *Next: rate both after training sessions.*
> - Categorized drill mix: **0 of 6** verified, categorized completions in the last 90 days — your assigned drills aren't linked to the catalog yet. *Next: ask your coach to assign from the drill catalog rather than free text, so completions can be categorized once verified.*

Each line is independently gated and independently unlockable — an athlete with a qualifying sparring-type mix but no categorized drills sees the sparring mix unlocked and the drill line still locked, never blocked by the other. No streaks, no timers, no variable reward, no comparison to any other athlete. This is the athlete's own record, described only in terms of what they have and what specific action produces more of it — matching the doctrine that engagement here means pride in one's own record, never compulsion.

Coach/org view, before org prerequisites are met, shows the same real-count shape: "**3 of 5** athletes have a qualifying sparring-type mix" with no names attached below threshold, and no composition rendered until the athlete-count floor (and, for drill mix, the distinct-category floor) is met.

## (d) What unlocks

**At athlete level (own record only)**

- Their own sparring-type composition: share of recorded `time_under_impact_sec` by `sparring_type`, over the chosen window — shown as recorded percentages of *their own logged segments*, explicitly labeled "your recorded mix," never a target or a grade.
- Their own physical-vs-cognitive load averages side by side (`rpe_physical`, `rpe_cognitive`), with `rated_by` visible — two facts, never merged.
- Their own verified, categorized drill-completion mix by `category`, `conditioning` broken out from all other categories combined.
- A plain factual notice whenever `pilot.training_holds` shows an active or historical hold with scope `conditioning_only`/`all_training` overlapping the shown window — context is always shown, never concealed by unlock progress, and progress-framed language is suppressed while a hold is active (see (a)).

**Locked forever, regardless of data volume:**
- Any target/ideal mix, "balanced"/"unbalanced" verdict, or comparison to any external ratio — unless and until the owner authors a specific target as a separate, explicitly-labeled doctrine input (open question 1); this engine never derives one itself.
- Any energy-system, aerobic/anaerobic, or "gas tank" label on any category — module 015's territory, refused there at any data volume, and refused here for the same reason.
- Any cross-athlete comparison, ranking, percentile, or leaderboard of any mix, at any level.
- Any AI-generated interpretation beyond restating the recorded shares (no "your balance is improving/off" sentence).
- Any auto-suggested training adjustment, progression, or medical/clinical inference drawn from a computed mix.
- Any per-athlete reading of `workout_template_items`/`session_script_blocks` content — those tables cannot honestly support an athlete-level claim (see (a) axis 4); this stays an org-only, library-only view forever.

**At org / coach level**

- Suppressed, org-wide composition rollups for each of the three athlete-level axes independently (sparring-type mix, load split, categorized-drill mix), gated by the 5-athlete floor (reusing `BOARD_MINIMUM_COHORT_SIZE`) and, for drill mix, the distinct-category floor — never a named list, never sorted by magnitude, never per-coach.
- The gym's own template-library content mix (`contact_level` / `block_kind` distribution across active templates and scripts) — explicitly labeled "what your library contains," never "what athletes received."

**Locked forever at org/coach level, regardless of data volume:**
- Individual athlete-level composition data ever surfaced to board/public aggregates (standing platform rule, restated here per module boundary).
- Any ranking or side-by-side comparison of athletes or coaches by mix — a bare per-coach or per-athlete composition table next to others' is a leaderboard by proxy even without a rank column.
- Any AI auto-approval of a doctrine target, progression decision, or medical/clinical inference.

## (e) Open questions for the owner

1. **Is there a house target mix, and who owns it?** Nothing in the schema or the honesty doctrine allows this engine to invent one. Options: (a) no target, ever — this engine stays purely descriptive forever; (b) coaching staff defines an explicit target mix (e.g., per program phase or age band), stored as a small, clearly-labeled doctrine reference table that this engine displays *alongside* the recorded mix, never blended into it; (c) defer any target entirely to module 036 (Periodization / Block Planning Engine, also currently an unbuilt DRAFT stub), since a phase-based target mix would naturally originate from block planning rather than from this reporting engine. **Recommend (a)** for v1 — ship the descriptive mix alone; revisit (b) only as a separate, explicit, opt-in doctrine layer if the owner wants a comparison, and treat (c) as the more likely long-term home for any target once 036 exists.

2. **How should 035 relate to module 015 once one of them is built?** Both read identical raw tables (`sparring_exposure`, `session_load`, drill/assignment tables) for adjacent-but-distinct questions (trend vs. composition). Options: (a) each module queries the raw tables independently, accepting some duplicated derivation logic; (b) whichever module ships first owns the per-category count/aggregation query, and the second module consumes its output rather than re-deriving identical counts a second time; (c) merge 015 and 035 into a single "Conditioning" module now, before either is built, since they overlap this heavily. **Recommend (b)** — per playbook rule 3 and AGENT_KERNEL invariant 2 (prefer existing primitives, search before creating), exactly one module should own "how many conditioned sparring segments did this athlete log this window," with the other reading that result.

3. **Org-level suppression floor.** Options: (a) reuse `BOARD_MINIMUM_COHORT_SIZE = 5` verbatim, as already adopted in `boardSummary.ts`; (b) pick a stricter floor for this module specifically (e.g., 10), on the reasoning that a multi-category composition breakdown can leak more information per athlete than a single count does; (c) defer entirely to modules 147/148/200 (Board Reporting, Program Outcome Reporting, Privacy Tier System) once built, since suppression policy is their assigned job. **Recommend (a)** now, with (c) as the eventual home — reuse the one suppression convention this platform has already shipped rather than inventing a second, possibly conflicting one.

4. **Should the categorized-drill-composition axis ship in v1 at all?** It is the one axis built on a non-DB-enforced vocabulary (`pilot.drills.category` has no `CHECK` constraint, unlike `sparring_type` or `contact_level`), and it depends on the newer `drill_id`-linked assignment path that most historical `drill_assignments` rows predate. Options: (a) include it now, clearly labeled as a softer, less-authoritative signal than the other two axes; (b) exclude it from v1 entirely, ship only the two DB-constrained axes (sparring-type mix, load split), and revisit once real volume accumulates through the `drill_id`-linked, verified-completion path; (c) first promote `pilot.drills.category` to a database `CHECK` constraint (a separate, small, owner-approved migration) before building on it here. **Recommend (b)** for v1 — ship the two axes the database itself already guarantees are meaningful; add the drill-category axis once the underlying data path has real, verified volume.
