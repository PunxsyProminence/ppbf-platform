## 4. How it works (proposed; the open choices are section 7's questions)

- **Who is listed (SC-1).** The caller must hold an active staff membership in the gym (else 403, not an empty list). From the gym's live roster: each athlete who is an active member (Q3), has come at least once (Q2), and whose last day they came is at least the gym's number of days ago.
- **"The last day they came"** is the later of (a) the register's last present day (`getAttendanceLast28Days`) and (b) the gym-local day of their last standing "here" mark on an **untied (open gym) run** (`session_script_runs.class_id` null). Tied runs are left to the register, as ATTENDANCE_PRECEDENCE.md says, so a later register change or a cancelled class is not overridden. The two are read apart and combined in the module, on this page only: `pilot.attendance_reconciled`, `getAttendanceLast28Days` and every attendance figure are unchanged (Q6.3 A; CT-13). `docs/current/ATTENDANCE_PRECEDENCE.md` gets one line recording this page-only reader.
- **The boundary (INFERRED from "no present mark for the gym's number of days").** With a gap of N days and today T, an athlete is listed when T minus the last day they came is N or more: no such day among the last N gym days, today included.
- **What a row shows:** name (opens the athlete's Passbook), the last day they came, days since. The fields are `last_came_day` and `days_since_came`, and the page says "came", not "present" or "attendance", so this page-only reading is not taken for an attendance figure. Nothing else: no age, date of birth, membership, payment or count. No new warning, gate or disclaimer (L1). The empty state says what was checked ("No one on the roster has gone N days without coming"), not that nobody is slipping.
- **The setting (SC-0a).** `pilot.organization_stopped_coming_policy`: one row per gym, `gap_days` with a CHECK of the allowed values (Q1), `set_by_account_id`, `set_at`. No row means 14 days. PUT `{ gap_days }` sets it; PUT `{ gap_days: null }` deletes the row so the default applies (the sizing's "Use the default" for SC-0b); both audited with the old and new value. The allowed list lives in the server module; the GET returns it as `choices` with `is_default`, and the drawer imports nothing from `src/server`, so no shared file and no `ci-classify-paths.mjs` edit.
- **The mark (SC-3a).** `pilot.athlete_reached_out_marks`, shaped on rest marks (Q4): who and when, no text; one current mark per athlete; clearing keeps the row (`cleared_at`, `cleared_by_account_id`); every change audited (`shadow_mirror: false`); a schema-ownership test pins the columns; the table joins `PUBLIC_SURFACE_FORBIDDEN_TABLES` and gets a `DATA_RETENTION.md` row ("Period not yet ruled"). The GET returns the marker's display name, never an account id. The page shows "Reached out by (name) on (date)" only while the mark is newer than the athlete's last day they came, so an athlete who came back and stopped again starts clean. It does not read the presence table.
- **Where SC-1's code lives:** a new `src/server/pilot/stoppedComing.ts`. Not in `attendancePrecedence.ts` ("Every function here counts rows in the view; none of them touches an underlying table", `:19-22`), and not in `sessionRunAthletes.ts` (W4-7's "Here" tap retries may touch it; INFERRED from the brief's item list, not checked).

### Q3
QUESTION FOR Jason: on the "stopped coming" list, which record makes an athlete an "active member" (your OW27-31 A)?
Asked of Jason, not Overwatch, because it reads his own words "Active membership" and decides who appears.
- **A (Recommended): the athlete is not marked as left the gym** (the admin's "This athlete has left the gym" control, `app/admin/athletes/page.tsx:940`; `pilot.athletes.active_flag`). Pros: matches the card's "or have left"; every athlete has this record; coaches' list is not shaped by the admin-only membership record ("Admin-only in both directions", `programMemberships.ts:14`). Cons: a lapsed program membership, or a track set to "Inactive", does not take an athlete off; the admin page's line "it does not take them off their coach's lists" (`:948-949`) must change for this list.
- B: as A, and the athlete's track is not "Inactive - on the roster but not attending" (`pilot.athletes.gym_status`, `app/admin/athletes/page.tsx:85-89`). Pros: someone the gym already marked as not attending is not listed again. Cons: an athlete set to Inactive by hand is never listed, even if no one has reached out; the same admin-page line changes.
