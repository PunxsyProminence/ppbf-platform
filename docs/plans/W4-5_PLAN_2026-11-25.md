## 2. Findings that shape the build

1. **No run-time gate reads a block's contact level** (OBSERVED by `grep` of `contact_level`
   and `contact_structure` over `apps/web/app` and `apps/web/src`; a search, not a run).
   The clearance gate reads observations, not plans (`contactClearanceGate.ts:32-36`).
   The plan label is shown on Session Plans (`page.tsx:636`) and carried in the reader
   projection (`sessionScriptProjection.ts:112`, `:131`).
2. **Two content rules do bind a block's contact level** (OBSERVED):
   - `step_contact_above_drill` (`contentImport/validate.ts:828`): a step may not link a
     drill at more contact than the drill's own `contact_level`.
   - `drill_contact_below_steps` (`drillLibraryEdit.ts:405-442`): a drill may not be lowered
     below a block of a plan's newest version that links it.
   SP-1a and SP-1b keep both: a new or copied block never carries more contact than its
   linked drill row. See question 1 and question 4.
3. **The edit path never recomputes the plan's contact label** (OBSERVED): in place it writes
   only name and minutes (`sessionScriptAuthoring.ts:476-482`); a new version copies the
   label (`:509-511`). SP-1a and SP-1b recompute it with `contactStructure` (`:116-122`) when
   the block set or order changes. INFERRED rule: a stored `observation_only` (a vocabulary
   value, `contentImport/vocabularies.ts:143`, that `contactStructure` never produces) is
   kept while every block is `none`, so the recompute never drops it for an equal label.
   `grep` finds no repo seed using it; production UNKNOWN.
4. **A move needs a two-pass renumber** (OBSERVED): `pilot_ssb_order_uq` is a plain unique
   constraint, not deferrable, and `block_order > 0` (migration `:71`, `:96`). In place, the
   kept blocks are first shifted above the current largest order, then written in their final
   order, in one transaction.
5. **Removing a block in place deletes a row** (OBSERVED: the module says "nothing here deletes
   a row", `sessionScriptAuthoring.ts:18-20`). Under "versioning as today" (the sizing), a plan
   nobody has run is changed in place, so its removed block's row is deleted. Two foreign keys
   name a block row, neither with `on delete`:
   - the run cursor (`session_run_state` migration `:120-125`). INFERRED safe: a plan with no
     run has no cursor, and the run check (`:466-471`) runs under the plan's row lock (`:373-406`).
   - a research transfer claim (`transfer_claims` migration `:64-65`), which content import can
     attach to a block (`contentImport/specs/transferClaims.ts:44`). Measured on the repo seed:
     0 of 173 claims name a block; production UNKNOWN. See question 3.
   Behaviour windows name a block by id with no foreign key, checked on insert only
   (`behaviour_sample_windows` migration `:124-128`). UNVERIFIED that a window can name only a
   block of its own run's plan; SP-1a checks this before it deletes anything.
6. **Block minutes and block order are separate columns** (OBSERVED, migration `:71-76`), and
   the server does not check that they agree. Measured on the repo seed (3 plans, 78 blocks):
   no gaps, no overlaps, starts in order. See question 2.
7. **No drill picker exists to reuse** (`grep` over `app/`, `components/`, `src/`). Both drill

## 5. Questions (also posted as PR comments, one each)

All to App Overwatch. Checked, not answered in: `docs/current/OWNER_DECISIONS.md`
(OD-2026-11-21-006, OW27-28, OW27-29, OW27-36; searched for contact_structure, contact label,
text block, copied block, reorder and remove), `docs/research/app-scrub-2026-11-19/` (the
CF-11 rows of stage 1 and stage 3), `W4_SIZING.md` section 5, the brief, and this PR's comments.

1. **What contact level does an added block carry?**
   - **A (Recommended):** a drill block, its drill's own level (the most the content rule
     allows); a text block, `none` (the column's default; the sizing's INFERRED reading); a
     copied block, its source's (the sizing). No new control. Con: a text block written for
     contact work would read as no contact, and so would the plan's label.
   - B: the coach picks the level: for a drill block at or below the drill's, for a text block
     from the contact ladder with no default. Con: two more controls; a pick can understate.
   - C: A for drill and copied blocks; B for text blocks.
2. **When a block is added, removed or moved, what happens to the minutes?** The editor
   proposes them in the same form, before Save; the server stores what is saved.
   - **A (Recommended):** each block keeps its length and the blocks from the change on run on
     from the block before them. A new block goes last, starting where the last block ends,
     5 minutes long (`DEFAULT_STEP_MINUTES`, what a template step with no minutes gets).
     Con: a deliberate gap or overlap after the change is closed (none in the repo seed).
   - B: only the order changes; every block keeps its minutes; the coach re-times by hand.
     Con: a moved block can show a time out of running order.
   - C: every change re-times the whole plan from minute 0. Con: closes every gap and overlap.
3. **A block a research claim names, on a plan nobody has run: how is it removed?**
   - **A (Recommended):** the removal is saved as a new version; the claim stays on the version
     it was written for, as it already does when a delivered plan is edited.
   - B: refused; nothing is saved, and the editor says why.
4. **Do the two content rules count as a "contact gate" for SP-2a and SP-2b?** (Section 2,
   findings 1 and 2.)
   - **A (Recommended):** no. They are label rules held in the server (SP-1a, SP-1b, Opus, two
     reviewers); no gate on an athlete reads a block's contact level. SP-2a and SP-2b stay
     Sonnet with one reviewer.
   - B: yes. SP-2a and SP-2b move to Opus with two adversarial reviewers.
