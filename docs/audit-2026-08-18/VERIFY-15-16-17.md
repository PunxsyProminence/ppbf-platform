#### Clause 1 — "of every uploaded video": **HOLDS, on the deployed configuration only**

I traced every condition that gates the vision call and there are six, not
zero. The pass states none of them, which makes the clause read as structural
when it is configuration-dependent.

1. `PPBF_VIDEO_CONTENT_SCAN` must be *exactly* the string `vision`. Anything
   else — unset, misspelled, `off`, `true` — yields `content: 'off'`:

   > `    content: contentRaw === 'vision' ? 'vision' : 'off',`
   > — `apps/web/src/server/pilot/videoScanPolicy.ts:95`

   **There is no third mode.** `export type ContentScanMode = 'vision' | 'off';`
   (`videoScanPolicy.ts:21`). So the answer to "is `vision` the only mode" is
   yes, and the other mode is a total no-op: `scanVideoSession` short-circuits
   the call at `videoScan.ts:184` before any blob read, and with malware also
   off the sweep returns `skippedReason: 'not_configured'` without touching the
   database at all (`videoScanSweep.ts:106-108`).
2. `isFilmStudyVisionConfigured()` must be true — deployment name **and**
   endpoint **and** key all non-empty (`shadowFilmStudy.ts:42-50`). Any one
   missing and `runContentScreen` returns `null` at `videoScan.ts:125-127`,
   before the blob download at `:131`. **No frames leave, no blob is read.**
3. `PPBF_SHADOW_WORKER_ENABLED === 'true'`, or the sweep never runs
   (`shadowJobWorker.ts:28`, `instrumentation.ts:27-29`).
4. The row must be claimable: `status = 'quarantined'` and
   `scan_state = 'pending' and scan_next_attempt_at <= now()`
   (`videoSessions.ts:158-161`). Uploads qualify — they are inserted
   `'quarantined'` (`video/upload/route.ts:85`) and the column defaults to
   `'pending'` (`infra/azure/pilot_slice_postgres_video_sessions_migration.sql:153`).
5. `ffmpeg` must decode the file and emit at least one frame, or `extractFrames`
   throws `SHADOW_FILM_FFMPEG_FAILED` (`shadowFilmStudy.ts:159-161`) and the
   catch returns `null` — **again before any transmission**. `ffmpeg` is
   installed in the runtime image (`Dockerfile:35`), so this normally passes.
6. `downloadPilotVideoFile` must succeed (`videoScan.ts:131`).

All six hold on production as the workflow writes it. I re-derived that rather
than taking it from the pass:

> `              PPBF_SHADOW_WORKER_ENABLED=true \`
> — `.github/workflows/deploy-production.yml:437` (`:467` on current `origin/main`)

**My refutation, and it partly succeeds.** The pass opens by asserting *"The

### HIGH-1 — a blocked video's safety escalation files once, and a failed write loses it "forever" — **CONFIRMED**

I looked hard for the retry, the transaction and the sweep, because "forever" is
the word that ought to break. It does not.

**Every quote is character-exact** at the cited lines: `videoScanSweep.ts:159-164`,
`videoSessions.ts:158-162`, `videoScanPolicy.ts:205-210`,

**Is there a retry?** No. `fileEscalation` has no internal retry and does not

> `export async function fileEscalation(input: FileEscalationInput, client?: PoolClient): Promise<SafetyEscalationRow> {`
> — `apps/web/src/server/pilot/escalationLadder.ts:158`

opening its own `withTransaction` when no client is passed (`:162-165`), and the
sweep passes none. A throw propagates.

**Is there a transaction spanning settle and escalation?** No — and this is the
mechanism. `settleVideoSessionScan` runs its own statement and commits
(`videoSessions.ts:209-230`); `fileEscalation` then opens a *separate*

failing escalation cannot roll the verdict back into a re-scannable state. That is
stated in the code comment as a virtue, and it is exactly what makes the loss
permanent.

**Is there a sweep that would re-file it?** I traced this three ways and all three
dead-end:

1. The **claim predicate** cannot match the row. After a terminal negative verdict
   `scan_state` is `'blocked'` / `'infected'` / `'needs_human_review'`, and
   `claimNextVideoSessionForScan` matches only `'pending'` or a stale `'scanning'`
   (`videoSessions.ts:160-161`). Never re-claimed, never re-scanned, never
   re-filed.
2. There is **one filer** for `source_type: 'video_scan'`. My own grep over
   `apps/web/src` and `apps/web/app`, excluding tests, returns four hits: the union
   type (`escalationLadder.ts:29`), two comments, and `videoScanSweep.ts:173`.
3. There is **no manual create path**. I read
   `app/api/pilot/escalations/route.ts` — the POST accepts only `acknowledge` and
   `resolve` actions (`:86-120`); nothing there files a new escalation. So a human
   who noticed the gap could not even re-file it by hand.

**Refutation that partially succeeds**, and the pass already concedes it: the
*video* does not disappear. `/admin/video-review/page.tsx` lists quarantined
sessions with `scan_state` and `athlete_id`, so the refused footage remains

"What is lost is that anybody is *told*" — is precise and I confirm it.

**The code comment being wrong is itself worth filing.**
`videoScanSweep.ts:161-162` asserts "the sweep tick retries". It does not, for any

**Confirmed at HIGH.** The pass's own open question (#4 — whether the worker runs

### HIGH-2 — a lease-expiry retry re-sends a child's video frames — **CONFIRMED**

The retry path and the lease-expiry mechanism both check out, verified from the
SQL rather than from the pass.

The lease reclaim is exact at `shadowJobQueue.ts:329-336`, and I read the whole
CTE: `stale_running` fires on `WHERE status = 'running' AND (lease_expires_at IS
NULL OR lease_expires_at <= NOW())` (`:354-355`), sets `status` back to
`'pending'` while retries remain, and — decisively for this finding —
**preserves `input_payload`**:

> `           input_payload = CASE`
> `             WHEN retry_count + 1 >= max_retries THEN '{}'::jsonb`
> `             ELSE input_payload`
> — `apps/web/src/server/pilot/shadowJobQueue.ts:336-338`

so the re-claimed job carries the same `videoSessionId` and blob path and does the
same egress. `JOB_LEASE_SECONDS = 300` (`:108`) against a 120-second provider
timeout plus a 60-second ffmpeg timeout plus a blob download — the pass's "can
approach" is fair. `max_retries` default 3 is confirmed in the DDL:

> `  max_retries integer not null default 3 check (max_retries between 1 and 10),`
> — `infra/azure/pilot_slice_postgres.sql:995`

**Refutations attempted, all failed.**

1. *Does the executor short-circuit when a proposal already exists?* No. The
   `on conflict (job_id)` idempotency the pass correctly credits
   (`shadowFilmStudyProposals.ts:83-84`, exact) is at the **persistence** step,
   which runs *after* `analyzeFramesWithVision`. Nothing reads
   `shadow_film_study_proposals` before the vision call. Order verified by reading
   `executeFilmStudyJob` end to end (`shadowJobProcessor.ts:873-...`).
2. *Does anything re-check consent on the retry?* No. `executeFilmStudyJob`'s only
   gates are a role allow-list (`:876-878`) and `isFilmStudyVisionConfigured()`
   (`:879-883`); `processNextShadowJob` adds actor role and athlete-scope
   re-validation (`:172-178`). No consent call exists anywhere on the async path,
   which I confirmed by the same inverted grep used for E-01 — four consent call
   sites, none in the processor, queue or worker.
3. *Does the withdrawal sweep cancel the job?* No.
   `suppressPublishedMediaForAthlete` (`publication.ts:357` onward) touches
   publications and library rows; it never reads `pilot.shadow_jobs`.

**One thing the pass understates.** Because the reclaim only requires the lease to
have lapsed — not the original execution to have stopped — a long-running
execution can have its job re-claimed *while it is still running*. `completeJob`
requires a live lease (`shadowJobQueue.ts:429`), so the original attempt's write
loses; but its egress already happened. So the worst case is **overlapping**
vision calls on the same child's footage, not merely sequential ones.

**Citation defect.** The pass presents this block as
`shadowJobProcessor.ts:900-905`:

> `    const videoBytes = await downloadPilotVideoFile(context.blobPath);`
> `    const clipPath = path.join(workDir, 'source-clip');`

The strings are exact but they live at **`:892-896`**. Line 900 is blank; `:901`
begins the `analyzeFramesWithVision` call. Similarly `max_retries` default `3` is
cited at `shadowJobQueue.ts:244`; it is on `:245`.

**Confirmed at HIGH.**

## What these passes missed

Six things I found while trying to break the findings, none of which appears in
any of the three passes. They are recorded here as observations for whoever owns
the next pass, not filed as findings.

**1. A third writer of `status = 'ready'` that no pass opened.**
Pass 15's method lists `api/pilot/video/[videoId]` and `video/review-link` as read
in full. `app/api/pilot/video/[videoId]/release/route.ts` is neither, and it is the
most consequential of the three: a **coach** — not an admin — may promote a
quarantined video of a minor to distributable state:

> `    requireRole(principal, ['organization_admin', 'coach']);`
> — `apps/web/app/api/pilot/video/[videoId]/release/route.ts:42`

> `       set status = 'ready', updated_at = now()`
> — `apps/web/app/api/pilot/video/[videoId]/release/route.ts:98`

There is no consent check on it. A coach may only release footage they uploaded
(`:59-61`) and only from a deferring `scan_state` (`:81-91`), which are real
controls — but this is the route that falsifies E-01's "only path" clause, and
three passes covering egress, consent and resilience all walked past it.

**2. A load-bearing comment that states a falsehood, of exactly the class E-04
files.**

> `  // Uploads are born 'quarantined' pending scan (#125). Film Study refuses`
> `  // anything that has not reached 'ready', so an unscanned or infected file`
> `  // is never opened by the worker. The scan sweep (#49) is the only thing in`
> `  // the platform that writes 'ready'.`

**3. A latent hole guarded only by a caller that does not exist.**
`HUMAN_RELEASABLE_SCAN_STATES` includes `'unconfigured'`
(`video/[videoId]/release/route.ts:21`), the `scan_state` written for the

unreachable, because the only caller of `scanVideoSession` is the sweep and the
sweep returns before claiming any row when nothing is configured
(`videoScanSweep.ts:105-108`). The moment anyone adds a second caller — an ops
route, a backfill script, a manual re-scan button — every quarantined video in an
unconfigured environment becomes coach-releasable with no scan of any kind. The
guard is an accident of call graph, not a control.

**4. A refused video with no athlete linked files no escalation at all — by
design.** Pass 17's HIGH-1 is about an escalation *lost to a failed write*. There
is a second, larger class it does not cover:

> `    if (terminal && isEscalatingScanDecision(scan.decision) && claim.athlete_id) {`
> — `apps/web/src/server/pilot/videoScanSweep.ts:170`

`athlete_id` is optional at upload (`video/upload/route.ts:64`, passed straight to the insert at `:90`), so an

no escalation ever — not through failure, but because `safety_escalations.athlete_id`
is NOT NULL. The code documents the skip; no pass asks what happens to that
refusal instead.

**5. The fact that would settle E-01's severity is filed as a footnote.**
E-01's remedy is stated as disclosure, and its *Could not establish* #3 records
that the Azure OpenAI deployment's retention posture is unknown. Those are the
wrong way round. Whether the deployment has abuse-monitoring retention or is
zero-retention determines how long frames of a child persist outside this
platform's control, and therefore whether the owner is deciding about a
disclosure gap or about a data-residency incident. That is one question to the
Azure resource owner, and it should be the first line of the escalation rather
than item three of a list nobody reads to the end.

nothing. No minor's data is on that payload, so this is an inconsistency rather
than an exposure — but it is the same inconsistency E-05 files, on a route E-05
did not look at.
