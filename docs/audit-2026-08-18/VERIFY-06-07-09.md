### P6-02 [HIGH] The retention hard-delete cannot succeed: foreign keys with no `on delete` action block the purge

**Verdict: CONFIRMED WITH CORRECTION** — severity stays **HIGH**. The headline
count "two foreign keys" is materially wrong, in the direction that makes the
problem *larger*.

**My own evidence.** I re-derived the FK census with a script over
`infra/azure/*.sql`, checking each `references` line plus the two lines after it
for an on-delete action (multi-line constraint bodies put the action on its own
line):

- `pilot.athletes`: **74** inbound FK references. **73** carry `on delete
  cascade`; **1** carries no action at all. The one is exactly the constraint the
  finding names, and it is character-exact at the cited lines:

> `  constraint pilot_one_percent_nominations_athlete_fk`
> `    foreign key (organization_id, athlete_id) references pilot.athletes(organization_id, athlete_id),`
> — `infra/azure/pilot_slice_postgres_one_percent_club_migration.sql:61-62`

- `pilot.accounts`: **127** inbound FK references — **34** `on delete cascade`,
  **27** `on delete set null`, and **66 with no on-delete action at all.**

The `pilot.parents.account_id` reference the finding names is one of those 66,
and is character-exact:

> `  account_id text null references pilot.accounts(account_id),`
> — `infra/azure/pilot_slice_postgres.sql:267`

and it sits inside `create table if not exists pilot.parents (` at
`pilot_slice_postgres.sql:264`, which is what makes it the always-populated one:
every guardian invite writes the row —

> `        `insert into pilot.parents (organization_id, parent_id, account_id, full_name, email)`
> — `apps/web/src/server/pilot/staffProvisioning.ts:470`

Both deletes plus the audit insert are one transaction
(`apps/web/scripts/pilot-cleanup-deleted-data.mjs:85` `await
client.query('begin');` … `:154` `await client.query('commit');`), with the
athlete delete first at `:131-132` and the account delete at `:136-139`, and the
failure path emits an identifier only:

> `      event: 'retention.cleanup.failed',`
> `      reason: error instanceof Error ? error.name : 'UnknownError',`
> — `apps/web/scripts/pilot-cleanup-deleted-data.mjs:168-169`

**Strongest refutation I could construct, and why each failed.**

1. *Something pre-deletes the referencing rows so the purge succeeds anyway.*
   Failed, and I checked both implementations. `purgeExpiredDeletedData`
   (`dataDeletion.ts:199-249`) issues exactly two `delete` statements plus the
   audit insert. The CLI (`pilot-cleanup-deleted-data.mjs:80-175`) issues one
   count, two deletes, one audit insert, `commit`. Neither touches
   `pilot.one_percent_nominations` or `pilot.parents`. There is no
   `on delete cascade` to lean on and no manual cleanup.
2. *The constraints are `deferrable`, so the check comes at commit and the
   ordering saves it.* Failed harder than the finding claims: `grep -rn
   deferrable infra/azure/*.sql` returns **nothing at all** — no constraint
   anywhere in the schema is deferrable.
3. *A later migration adds the cascade.* Failed. `one-percent-club` is genuinely
   the final element of the `all` loop —
   `for m in multiorg … attendance-precedence one-percent-club; do`
   (`.github/workflows/apply-migrations.yml:279`) — and `grep -rn "alter table
   pilot.parents" infra/azure/*.sql` returns nothing.
4. *The blocking table is dead, so no rows ever exist.* Failed. Nominations are
   written by live code — `insert into pilot.one_percent_nominations (`
   (`apps/web/src/server/pilot/onePercentClub.ts:275`) behind
   `apps/web/app/api/pilot/coach/one-percent-club/route.ts`.
5. *Fixed by a merge since the pass ran.* Failed. No merged PR alters either
   constraint or adds a pre-delete.

**Corrections the finding needs.**

- **"Two foreign keys with no `on delete` action" is wrong.** It is accurate for
  the athlete half (1 of 74) and wrong for the account half: 66 of 127 inbound
  FKs to `pilot.accounts` carry no action. The finding presents
  `pilot.parents.account_id` as *the* blocker rather than as the one that is
  guaranteed to be populated. Choosing the always-populated instance as the
  existence proof is sound method; stating the census as "two" is not, and it
  understates how much work fixing this is.
- **"Cannot succeed" needs one qualifier.** The purge short-circuits before any
  delete when there is nothing due: `if (total === 0) { await
  client.query('rollback'); … 'retention.cleanup.completed' }`
  (`pilot-cleanup-deleted-data.mjs:126-129`). So an empty run reports success
  honestly. The precise claim is: *any run with a due parent account aborts*
  (guaranteed, via `pilot.parents`), and *any run with a due athlete who was ever
  nominated aborts* (conditional). Both abort the whole transaction for every
  family in it. Stated that way the finding is airtight; stated as an
  unconditional "cannot succeed" it is refutable on an empty database.
- **The design-comment quote is reflowed.** The finding renders the file's
  reasoning as *"Nothing is deleted to resolve a nomination -- a withdrawal
  stays on the record"* citing `:65-66`. The file has it across two lines with a
  trailing clause the quote drops:
  `  -- Nothing is deleted to resolve a nomination -- a withdrawal stays on the`
  (`:65`) / `  -- record, and it has to say why.` (`:66`). Joined and truncated
  inside quote marks.

The workflow quote is exact: `#   The dry run is not busywork: it is the
monitor. A number that climbs` (`.github/workflows/retention-cleanup.yml:35`).

**Why severity holds at HIGH.** Direction of failure is safe (nothing
over-deleted), but a published retention commitment is unexecutable and the
only signal is an error *name* in a CI log. The correction raises the remediation
cost rather than lowering the risk.

## What these passes missed

Things I established while trying to break the findings that none of the three passes
records. Each is a fact about the current tree, not a new finding write-up.

**1. There are two incompatible soft-delete semantics, and neither pass names the
divergence.** The right-to-be-forgotten API route sets `deleted_at` and nothing else
(`apps/web/src/server/pilot/dataDeletion.ts:64`). The operator CLI sets `deleted_at`
*and* clears `active_flag` *and* revokes sessions — its header says so:
`" *   SOFT DELETE ONLY       Sets deleted_at, clears active_flag, revokes"`
(`apps/web/scripts/pilot-cleanup-accounts.mjs:29`), implemented at `:247-252`. Two
paths, one word ("delete"), two meanings, and only one of them stops a login. Pass 6
reports the login consequence but frames it as a universal property rather than a
divergence between two implementations — which matters, because the fix is to make the
route do what the CLI already does, not to invent a filter.

**2. `pilot.accounts` has 66 inbound foreign keys with no on-delete action, out of
127.** Pass 6 reduced the account-side purge blocker to a single named FK. The census
(34 cascade / 27 set null / 66 none) is a schema-wide referential-integrity picture
that no pass states, and it is the number that determines how large the retention fix
actually is.

**3. `apps/web/scripts/pilot-approve-library-baseline.mjs` is the one place in the
repository that filters `deleted_at` correctly, and it wrote down why.** `        and deleted_at is null`
(`:151`), under the reasoning "*An inactive or soft-deleted owner is not eligible -- an
attestation by an account that cannot sign in is not an attestation*". Pass 6's
enumeration explicitly denies any such case exists ("all four are inside
`dataDeletion.ts`"), which erases the codebase's own precedent for the fix.
